## 威胁模型

信任边界：

1. **Ring-3 → Ring-0 syscall/ioctl**：普通用户态任务通过 `int $0x80` ABI 进入内核。
2. **不受信任网络输入 → 内核协议栈 / libc HTTP 解析器 / 浏览器**。
3. **普通进程 → 桌面/系统服务 → 持久化配置与电源状态**。
4. **二层同网段恶意节点 → DHCP/ARP/TCP**。
5. **受保护 HTTPS 端点 → HTTP（协议降级）**。

攻击者能力：

- 能够编译/运行公开 LeonOS ABI 的用户态程序（非管理员/非服务权限）。
- 能够向浏览器/HTTP 客户端提供不受信任的 HTTP(S) 响应，或在同一二层链路发送以太网帧。
- 不假设物理访问、Secure Boot 绕过或离线修改 loader。

安全目标：

- 任意用户进程不能无授权地关闭/重启整个操作系统。
- 任意用户进程不能绕过 VFS 权限模型写入系统目录或 EFI 引导分区。
- HTTPS 下载的传输完整性不能被合法重定向响应降级为明文 HTTP。
- 网络协议解析器与内核协议栈不得因受控输入产生越界内存访问或全局状态错配。
- DHCP 状态机必须绑定 OFFER 的服务器；同网段攻击者不能抢在合法服务器之前伪造 ACK 劫持全局网络配置。
- 浏览器 Basic 认证作用域必须包含 URL 方案；凭据不能从 HTTPS 会话泄漏到明文 HTTP。
- 同一二层 ARP 缓存不得接受未请求、未关联的发送者映射。
- 已建立 TCP 连接不得被任意序号的伪造 RST 直接关闭。

## 发现详情（准入严格版）

### [F1] 电源控制 IOCTL 缺少授权检查（任意进程可触发内核级重启/关机）

| 字段 | 值 |
| --- | --- |
| 严重性 | **中等（本地全系统 DoS，跨用户边界）** |
| 置信度 | 高（直接源码控制流证据 + 邻近对比反例） |
| 分类 | CWE-862（缺少授权） |
| 受影响位置 | `kernel/ntclks/syscall.c:4947-4953` |
| 邻近授权正例 | 同文件 `LEONOS_GUI_IOCTL_TASK_KILL`（`syscall.c:4883`）调用 `authz_check_path(..., LEONOS_AUTHZ_KILL_TASK, ...)`；`LEONOS_IOCTL_NET_DHCP`（`syscall.c:5207`）调用 `require_network_config_access()` |

#### 端到端利用路径（Source → Sink）

1. **入口**：任意可执行 `int $0x80` / LeonOS libc 的 Ring-3 任务调用 `LINUX_SYS_IOCTL`，将 `a1` 设为 `LEONOS_GUI_IOCTL_REBOOT`（常量 `0x4c524254`）或 `LEONOS_GUI_IOCTL_SHUTDOWN`（`0x4c534844`）。`a2` 未被使用，无需有效用户指针。
2. **分发**：内核进入 `syscall_dispatch_regs`，匹配分支：
   - `syscall.c:4947`：`if (number == LINUX_SYS_IOCTL && a1 == LEONOS_GUI_IOCTL_REBOOT) { power_reboot(); }`
   - `syscall.c:4951`：`if (number == LINUX_SYS_IOCTL && a1 == LEONOS_GUI_IOCTL_SHUTDOWN) { power_shutdown(); }`
3. **授权检查缺失**：这两个分支**直接**调用平台电源例程；**不**经过 `require_window_server()`、`require_network_config_access()`、`authz_check_path()`、`require_driver_management()` 或任何 `task_effective_role()` 检查。对比文件内其它特权操作（`TASK_KILL`、`DRIVER_CONTROL`、`NET_DHCP`、`FB_*`、`DISPLAY_*` 等）均有明确守卫。
4. **SINK**：`power_reboot()`/`power_shutdown()` 触发平台级重启或关机。

#### 影响与可信边界

- 跨用户与跨服务：**任何**登录会话内任意低权限用户代码均可导致全系统失去可用性。
- 不满足提权或机密性泄露标准，**不升为严重**；但作为可被无权限进程直接触发的「全系统 DoS」，达到中等且端到端链完整。

#### 修复建议

- 为 REBOOT/SHUTDOWN 分支前置一个 `require_power_control()` 守卫，语义为：installer_mode 内可放行；否则调用者必须是 `LEONOS_AUTH_ROLE_ADMIN` 或携带显式 `LEONOS_AUTHZ_POWER` 策略；或仅限受信任窗口服务器转发的、已完成桌面 UI 授权确认的请求。
- 回归测试：普通进程调用两个 IOCTL 应返回 `-LEONOS_EPERM`；以管理员/服务身份调用仍能到达 `power_*`。

### [F2] HTTPS → HTTP 降级重定向未被拒绝（下载与浏览传输完整性破坏）

| 字段 | 值 |
| --- | --- |
| 严重性 | **中等（破坏用户预期的传输完整性；可辅助安装包/更新包替换）** |
| 置信度 | 高（静态调用链 + 位置值匹配） |
| 分类 | CWE-319（明文传输敏感信息）、CWE-757（算法/协议降级攻击） |
| 受影响位置 | `userland/libc/src/libc.c:3362-3404`（`leonos_http_request` 重定向循环）+ 浏览器重用该库的全部浏览/下载路径 |

#### 端到端利用路径（Source → Sink）

1. **受害者触发**：调用 `leonos_http_request`（libc HTTP 入口）或通过浏览器、下载管理器发出 HTTPS 请求。`current_url` 初始为形如 `https://example.com/package.zip` 的 URL。
2. **HTTP fetch 完成**：`http_fetch_once(current_url, request, response, location, ...)`（`libc.c:3375`）成功返回，响应状态满足重定向判断 `http_is_redirect(response->http_status)`（`301/302/303/307/308`），且 `Location` 头部被写入 `location`。
3. **恶意 Location 构造**：攻击者控制的 `https://example.com/` 响应中写入 `Location: http://example.com/package.zip`。`leonos_http_resolve_url` 在 `location_text` 以 `http://` 或 `https://` 开头时**直接原样拷贝**到 `next_url`，没有方案安全性比较语义。
4. **降级被无条件接受**：返回 `leonos_http_request` 的重定向循环，代码只做了 URL 解析失败与重定向次数检查（`libc.c:3396-3400`），随后执行 `http_copy_text(current_url, sizeof(current_url), next_url);`（`libc.c:3401`）。
5. **SINK**：循环的下一次迭代 `http_fetch_once(current_url, ...)` 发起的请求为**明文 HTTP**。链路攻击者即可查看和替换下载内容。

#### 影响论证

- `browser_http_request_with_cookies`（`userland/apps/browser/cookies.c`）在重定向过程中会对新的 `current_url` 再次调用 `browser_http_prepare_headers`，进而发送 Cookie 与 Basic 认证（参见 F5）；若认证头/敏感 Cookie 已写入，降级会造成凭据明文传输。
- 下载管理器 `downloadmgr`（调用 `leonos_http_get`）不区分初始与最终方案；对用户显示的仍是"从 HTTPS 发起"的原始意图，但实际写入磁盘的文件已不受 TLS 保护——可被替换为恶意安装包、可执行载荷、组件清单等。
- 是否能直接诱导代码执行取决于下载物的后续处理（未在本轮审计中证明签名验证缺位，因此不升严重）；但**下载内容完整性保证被系统性破坏**本身构成中等严重度。

#### 修复建议

在 `leonos_http_request` 的重定向循环中（`libc.c:3401` 之前），在跟随 `next_url` 之前：比较 `current_url` 与 `next_url` 的方案前缀；当 `current_url` 为 `https://` 且 `next_url` 为 `http://` 时，**立即中止**，将 `response->net_status` 置为新的 `LEONOS_NET_STATUS_REDIRECT_DOWNGRADE`。

### [F3] HTTP chunked 解码 `chunk_size` 乘法回绕 + 加法型边界绕过导致响应缓冲区越界读取

| 字段 | 值 |
| --- | --- |
| 严重性 | **中等（用户态进程受控越界读取；可致崩溃与敏感内存读取）** |
| 置信度 | 高（算术级回绕证明 + 源码位置） |
| 分类 | CWE-190（整数回绕/溢出）、CWE-125（越界读取） |
| 受影响位置 | `userland/libc/src/libc.c:2983-3033`（`http_decode_chunked`） |

#### 端到端利用路径（Source → Sink）

`http_decode_chunked(buffer, body_offset, raw_len, capacity, flags)` 的**每一步**均可被远程 HTTP 响应完全控制：

1. **响应触发**：只要 HTTP 响应的 `Transfer-Encoding: chunked` 被检测（`libc.c:3316` `http_contains_ignore_case(transfer_encoding, "chunked")`），`response->body_len = http_decode_chunked(...)` 即被调用。所有通过 `leonos_http_request`/`leonos_http_get` 的 HTTPS/HTTP 客户端都到达该解码器。
2. **`chunk_size` 回绕**：`chunk_size` 为 `uint32_t`（`libc.c:2990`）。解析循环：
   ```c
   while (src < raw_len && http_is_hex(buffer[src])) {
       chunk_size = chunk_size * 16U + http_hex_value(buffer[src]);  // line 2996
       ++src; saw_hex = 1;
   }
   ```
   只要提交 ≥ 9 个十六进制字符（例如长度前缀 `100000000` = 2^32），`chunk_size * 16U` 会对 `UINT32_MAX + 1` 模回绕，使 `chunk_size` 最终为一个**远小于解析位数声明**的小值。
3. **边界检查失效**：紧接着使用加法型上界 `if (src + chunk_size > raw_len)`（`libc.c:3012`）。当 `src` 接近缓冲区尾且 `chunk_size` 经回绕后变成可让 `src + chunk_size` 再次回绕为小值的量时，该比较为假，`chunk_size` 不会被截断为 `raw_len - src`。
4. **SINK 越界读取**：随后循环 `for (uint32_t i = 0; i < chunk_size; ++i) buffer[dst++] = buffer[src + i];`（`libc.c:3018-3025`）从 `buffer + src + i` 读取，i 上限可达回绕后的值。`src + i` 超出 `raw_len` 后继续向后访问该缓冲区边界之外：
   - 若 `buffer` 末尾紧邻未映射或只读页 → 进程段错误（浏览器/下载客户端/HTTP get 均被终止）。
   - 若后续页存在可访问内存 → 将后续堆/栈字节压缩复制到缓冲区前部，解码结果可被后续处理代码**读取并呈现/存储**，形成内存内容泄露通道。
5. **返回值**：`dst` 作为 `response->body_len` 返回给上层。上层 UI 或应用会按该长度消费 `response_body`，泄露的字节可被显示、写盘、再次通过网络回传等。

#### 修复建议

- 在十六进制累加前使用更宽类型（`uint64_t chunk_size64`），每一步执行回绕检测并拒绝超长输入。
- 把加法型边界检查替换为差值型（永远安全）：`if (src > raw_len || chunk_size64 > raw_len - src) { truncated; break; }`。

### [F4] DHCP ACK 未绑定已选择的 OFFER（同网段可抢 ACK 劫持全局配置）

| 字段 | 值 |
| --- | --- |
| 严重性 | **中等（可替换网关/DNS/租约地址 → 全系统中间人/拒绝服务）** |
| 置信度 | 高（源码函数级 ACK 等待控制流） |
| 分类 | CWE-345（身份/来源验证不足） |
| 受影响位置 | `kernel/ntclks/net.c:1837-1864`（`net_dhcp_wait`）、`1872-1922`（`net_dhcp_request`） |

#### 端到端利用路径（Source → Sink）

前置：内核发起 DHCP 续租/首次获取（OOBE 期间管理员服务、netctl 管理员调用 `LEONOS_IOCTL_NET_DHCP`；该 ioctl 入口现在受 `require_network_config_access()` 守卫，**不再是任意进程可调用**）。

利用链：

1. DISCOVER 发出后，合法与恶意 DHCP 服务器（同二层）均可返回 OFFER。`net_dhcp_request` 在 `net.c:1895` 等待第一个匹配 `xid` 的 NET_DHCP_OFFER。内核只等待"第一个匹配的 OFFER"，随后记录其 `offer.yiaddr` 和 `offer.server_ip`，并在 `net.c:1903` 以 `NET_DHCP_REQUEST` 明确发送到该 `offer.server_ip`。
2. 随后在 `net.c:1909` 调用 `net_dhcp_wait(xid, timeout_ms, NET_DHCP_ACK, &offer)`。该函数实现（`net.c:1837-1864`）：
   ```c
   while (!timeout) {
       udp_wait = { src_port = NET_DHCP_SERVER_PORT, dst_port = NET_DHCP_CLIENT_PORT, ... };
       net_poll_once(0, 0, &udp_wait, 0);
       if (udp_wait.done && net_dhcp_parse_packet(payload, udp_wait.length, xid, offer) == 0) {
           if (offer->msg_type == NET_DHCP_ACK) return 0;      // 接受
           if (offer->msg_type == NET_DHCP_NAK) return -3;
       }
   }
   ```
   **关键缺口**：
   - 不校验 ACK 报文的 `server identifier` 是否等于前一步 REQUEST 目标 `offer.server_ip`；
   - 不校验 ACK `yiaddr` 是否等于 REQUEST 请求过的地址；
   - 仅以 `xid` + 消息类型为接受条件。
3. **抢发送者优势**：攻击者只要位于同一二层、能发 UDP 67/68、观测或猜测 `xid`（DISCOVER/REQUEST 广播中 xid 是明文，攻击者可直接嗅探），即可在合法服务器 ACK 到达之前抢先发一个 `msg_type=ACK` 的报文，`offer` 出参被 `net_dhcp_parse_packet` 重写为攻击者提供的 `yiaddr/router_ip/dns_ip/server_ip/lease_seconds`。
4. **全局配置写入**：`net_dhcp_request` 不做复核，紧接着于 `net.c:1917` 调用 `net_apply_dhcp_offer(&offer)`，将 `net_config.local_ip`、`subnet_mask`、`gateway_ip`、`dns_ip`、`dhcp_server_ip`、`lease_seconds` 全部替换为攻击者指定值。
5. **SINK 影响**：DNS → 全部后续解析指向攻击者控制 DNS；网关 → 全部非本地流量被导向攻击者 MAC，与 F6（ARP 无条件缓存）配合即可完成全部出流量劫持；租约地址错误/不可达 → 全系统网络 DoS。

#### 修复建议

- `net_dhcp_wait` 扩展签名：`expected_server_ip, expected_yiaddr`，并在 accept 前校验两者匹配；丢弃不符合的 ACK 后继续等待合法 ACK。

### [F5] 浏览器 Basic 认证键不包含 URL 方案（HTTPS 凭据可发送到明文 HTTP）

| 字段 | 值 |
| --- | --- |
| 严重性 | **中等** |
| 置信度 | 高（字段/缓存结构级证明） |
| 分类 | CWE-523（凭据保护不足）、CWE-319（明文泄露） |
| 受影响位置 | `userland/apps/browser/auth.c:60-84`（`auth_entry_for` 与 `browser_auth_append_header`）、`auth.c:116-142`（写入条目，仅写入 host/port） |

#### 端到端利用路径（Source → Sink）

1. **凭据录入**：用户访问 `https://corp.example.com:443/admin`，服务端返回 `WWW-Authenticate: Basic`。浏览器弹 UI → 用户输入 `admin:password` → `browser_auth_retry_from_challenge`（`auth.c:86-142`）生成 `Authorization: Basic ...` 并存入缓存：
   - `index = auth_entry_for(parsed.host, parsed.port)`（`auth.c:116`）
   - 写入 `browser_auth_entries[index].host = parsed.host`；`.port = parsed.port`；`.header = "Authorization: Basic ..."`。
   - **不保存 `parsed.scheme`**，并且 `auth_entry_for` 签名和比较都只包含 (host, port) 两元组。
2. **导航到同主机端口的 HTTP**：可能触发情形之一：
   - 用户手动输入 URL `http://corp.example.com:443/...`；或
   - 网站首页 `<a href="http://corp.example.com:443/...">`；或
   - 结合 **F2（HTTPS 降级重定向）**：由 HTTPS 响应返回 `Location: http://corp.example.com:443/...`，`leonos_http_request` 无条件跟随（F2 已证），导致浏览器自动在降级的 HTTP 上请求。
3. **请求头生成**：`browser_http_prepare_headers` → `browser_auth_append_header(url, out, &pos, cap)`（`auth.c:71-84`）：
   ```c
   parse_http_url(url, &parsed);
   index = auth_entry_for(parsed.host, parsed.port);   // 仅 host/port
   if (index >= 0) append_text(out, pos, cap, header); // Authorization: Basic ...
   ```
4. **SINK**：该请求以明文 HTTP 发送，Authorization 头中的 Base64 可逆凭据被同网段嗅探者完整读取。凭据可被攻击者直接重放到 HTTPS 端点（反向仍可用），完成会话接管或敏感资源访问。

#### 组合增益

- 与 **F2** 组合可把"用户手动输入错误 URL"变成**全自动利用**：只要用户登录过一次 HTTPS 站点，攻击者只要让该 HTTPS 端点返回一个降级重定向，凭据就会在下一步明文发出。

#### 修复建议

- `auth_entry_for(host, port)` → `auth_entry_for(scheme, host, port)`，缓存结构同步加 `scheme` 字段；
- 在 `browser_auth_append_header` 中加入硬不变量：**若条目是从 `https://` 录入，当且仅当当前 URL 方案为 `https://` 才附加 Authorization**。

### [F6] ARP 缓存无条件存储入站 sender 映射（无需匹配未完成查询或链路一致性）

| 字段 | 值 |
| --- | --- |
| 严重性 | **中等（本地网段可稳定毒化网关 MAC）** |
| 置信度 | 高（源码行级控制流） |
| 分类 | CWE-345（邻居身份不充分校验） |
| 受影响位置 | `kernel/ntclks/net.c:1041-1067`（`net_handle_arp`），写缓存点 `net.c:1058` |

#### 端到端利用路径

1. **入站帧**：攻击者在相同二层广播域发送任意格式合法的 ARP 帧（Ethernet type 0x0806、HTYPE=1、PTYPE=0x0800、HLEN=6、PLEN=4）。
2. **控制流**：`net_handle_arp(frame, len, arp_wait)`：
   - 格式检查通过（`net.c:1048-1053`）；
   - 提取字段（`1054-1057`）：`op`、`sender_mac = frame + 22`、`sender_ip`、`target_ip`；
   - **无条件写缓存**：`net_arp_cache_store(sender_ip, sender_mac);`（`1058`）——先于后面第 `1059-1066` 行的 REQUEST 与 REPLY 相关逻辑。
   - 随后才判断是否为针对本机的 REQUEST、或是否匹配等待中的 `arp_wait->ip` 的 REPLY。
3. **关键缺口**：
   - 不需要该 sender_ip 正处于内核等待的 ARP 查询；
   - 不需要 `op == ARP_OPER_REPLY`；
   - 不对 **Ethernet 帧头 src MAC** 与 **ARP sender_mac** 一致性做校验；
   - 不做 Gratuitous ARP 的显式策略。
4. **SINK**：攻击者以广播 `sender_ip=GATEWAY_IP, sender_mac=ATTACKER_MAC` 的单个 ARP 请求（`op=ARP_OPER_REQUEST`，`target_ip=任意`）即可把 `net_arp_cache_store` 改写为攻击者地址。之后内核将所有非本地流量 `dst_mac = ATTACKER_MAC`。
5. **组合**：与 F4（DHCP ACK 抢注）结合 → 出流量全部被攻击者中继，可进行中间人嗅探/篡改；若攻击者不转发，则直接造成全系统网络不可用 DoS。

#### 修复建议

- 把 `net_arp_cache_store(sender_ip, sender_mac)` 从无条件位置（`1058`）后移到受约束分支：`op == ARP_OPER_REPLY && arp_wait && sender_ip == arp_wait->ip` 匹配成功时；或 `op == ARP_OPER_REQUEST && target_ip == local_ip && sender_ip 是本节点已有缓存项的"刷新"`。
- 在存储前增加以太网源 MAC == ARP sender_mac 一致性校验。

### [F7] TCP RST 缺少接收窗口序号验证直接关闭已建立连接

| 字段 | 值 |
| --- | --- |
| 严重性 | **中等（可跨连接泛洪中断会话）** |
| 置信度 | 高（行级控制流） |
| 分类 | CWE-345（协议状态机不充分） |
| 受影响位置 | `kernel/ntclks/net.c:1557-1560`（`net_socket_handle_tcp` 中的 RST 处理） |

#### 端到端利用路径

1. 任意已建立的 TCP 连接（`socket->state == LEONOS_NET_TCP_ESTABLISHED` 或 `TIME_WAIT`）均可被伪造的 TCP 报文关闭。
2. 内核在 TCP 入口解析完 `flags, seq, ack, payload_len` 后调用 `net_socket_handle_tcp(src_ip, src_port, dst_port, seq, ack, flags, payload, payload_len)`。
3. **状态转换**：`net_socket_handle_tcp` 首先执行匹配套接字查找 `socket = net_socket_match(src_ip, src_port, dst_port)`。这要求（src_ip, src_port, dst_port）匹配（本地端口多数情况下可从侧信道或共享链路直接嗅探获得）。
4. **缺口**：函数到达 `if (flags & TCP_FLAG_RST)`（`net.c:1557`）即调用 `net_socket_mark_closed(socket, LEONOS_NET_STATUS_TCP_RESET); return;`——**完全不读取/验证 `seq` 参数**（该参数作为函数形参传入但此分支内未使用），也不使用 `socket->remote_seq`（期望接收序号）做接收窗口判定。
   - 对比同函数中 SYN-ACK 建立（`1561-1567`）使用 `socket->acked_seq == socket->local_seq`；payload 数据接收（`1585-1601`）使用 `seq == socket->remote_seq`；FIN 处理（`1617-1620`）使用 `seq + payload_len == socket->remote_seq`。所有其他状态转换都有**明确序号匹配**；唯独 RST 没有。
5. **SINK**：攻击者发送一个四元组匹配、TCP 头含 RST 标志、**任意序号**的报文即导致连接状态置为 `LEONOS_NET_TCP_CLOSED`、状态 `TCP_RESET`。效果：进行中的浏览器 HTTPS 浏览、下载管理器长下载、任何 TCP 应用通信可被立即中断；对共享网络节点可泛洪式断开大量并发连接，形成稳定的应用层 DoS。

#### 修复建议

- 在 RST 分支插入 RFC 793 / RFC 5961 兼容的接收窗口判定：仅当 RST seq 落在当前可接受接收窗口内才关闭；否则忽略。

### [F8] 内核调试 IOCTL 缺少授权（任意进程可写入系统状态目录与 EFI 引导分区）

| 字段 | 值 |
| --- | --- |
| 严重性 | **中等（绕过 VFS 权限模型写入系统目录与 EFI 分区；可武装内核调试启动）** |
| 置信度 | 高（源码控制流 + 存储层权限绕过证据） |
| 分类 | CWE-862（缺少授权）、CWE-284（访问控制不当） |
| 受影响位置 | `kernel/ntclks/syscall.c:4449-4453`（IOCTL 入口）+ `kernel/ntclks/kernel_debug.c:491-534`（`kernel_debug_control`） |
| 邻近授权正例 | 同文件 `LEONOS_IOCTL_TIME_NTP_SYNC`（`syscall.c:5157`）调用 `require_background_service()`；`LEONOS_IOCTL_DRIVER_CONTROL`（`syscall.c:5330`）调用 `require_driver_management()`；`LEONOS_IOCTL_NET_DHCP`（`syscall.c:5208`）调用 `require_network_config_access()` |

#### 端到端利用路径（Source → Sink）

1. **入口**：任意可执行 `int $0x80` / LeonOS libc 的 Ring-3 任务调用 `LINUX_SYS_IOCTL`，将 `a1` 设为 `LEONOS_KERNEL_DEBUG_IOCTL_CONTROL`（常量 `0x4c4b4447`），`a2` 指向用户态 `struct leonos_kernel_debug_control`。
2. **分发**：内核进入 `syscall.c:4449` 的分支：
   ```c
   if (number == LINUX_SYS_IOCTL && a1 == LEONOS_KERNEL_DEBUG_IOCTL_CONTROL) {
       if (!user_range_ok(a2, sizeof(struct leonos_kernel_debug_control))) {
           return -LEONOS_EFAULT;
       }
       return kernel_debug_control((struct leonos_kernel_debug_control *)(uintptr_t)a2);
   }
   ```
3. **授权检查缺失**：该分支**仅**做了 `user_range_ok`（缓冲区有效性检查），**不**经过任何 `require_*()` 守卫、`authz_check_path()` 或 `task_effective_role()` 检查。对比文件内几乎所有其它"系统影响型" ioctl（电源、网络配置、驱动控制、NTP 同步、任务亲和性、显示/外观请求等）均有明确守卫。
4. **存储层权限绕过**：`kernel_debug_control`（`kernel_debug.c:491-534`）根据 `control->command` 执行：
   - `LEONOS_KERNEL_DEBUG_CONTROL_SET_ENABLED`（值 `2`）：调用 `storage_mkdir("/system")`、`storage_mkdir("/system/state")`、`storage_write_file("/system/state/kerneldebug.enabled", "1\n", 2U)`。这些 `storage_*` API 是**底层存储后端直写接口**（`drivers/bootstrap/storage/storage_vfs.c:1186`），**完全绕过** syscall 层的 `authz_check_path` → `osmlayer_fsacl_authorize` VFS 权限检查。
   - `LEONOS_KERNEL_DEBUG_CONTROL_ARM_NEXT_BOOT`（值 `3`）：先检查 `enabled`（即 `/system/state/kerneldebug.enabled` 是否存在），然后调用 `storage_write_boot_esp_file("/boot/system/state/kerneldebug.next", KERNEL_DEBUG_MARKER, ...)`，向 **EFI 引导分区**写入调试启动标记。
   - `LEONOS_KERNEL_DEBUG_CONTROL_CLEAR`（值 `4`）：删除上述两个文件。
5. **SINK（系统状态篡改）**：任意低权限进程可：
   - 在 `/system/` 下创建目录并写入 `/system/state/kerneldebug.enabled`，**无视该路径的 VFS ACL**（`osmlayer_acl_default_for_path` 对 `/system` 树仅授予 USERS 主体 `READ|EXEC`，正常 open/write 会被拒绝）。
   - 向 EFI 引导分区 `/boot/system/state/kerneldebug.next` 写入固定标记字符串。
6. **SINK（启动时内核调试模式）**：下次启动时，`kernel.c:284` 检查 `kernel_debug_boot_requested(handoff)`——该函数要求 `handoff->kernel_debug_mode != 0` **且** `/system/state/kerneldebug.enabled` 存在。两个条件攻击者均已满足。随后内核调用 `kernel_debug_run_module()`（`kernel_debug.c:908`），尝试从 `/system/kerneldebug.sys` 加载 ELF 模块并以**内核特权**执行其 `leonos_kernel_debug_module_entry`（API 包含 `power_reboot`、`power_shutdown`、TUI 全屏控制、benchmark 等）。

#### 影响等级说明

- **已确认的中等影响**：任意用户进程绕过 VFS 权限模型写入系统状态目录与 EFI 引导分区，并可武装内核调试启动模式。这是对文件系统访问控制完整性的直接破坏，跨用户/跨服务边界。
- **潜在提权路径（本轮未证明可独立达成）**：若攻击者能同时将恶意 ELF 写入 `/system/kerneldebug.sys`，则下次启动时获得内核代码执行。然而 `/system` 树的默认 ACL（`runtime.c:1498-1501`）仅授予 USERS `READ|EXEC`，正常 open/write 无法写入该文件；且 `kernel_debug_control` 不提供写入任意路径的能力。因此完整的内核代码执行链需要额外的写入 `/system` 的能力（如管理员操作或另一个漏洞），不单独升为严重。
- 即便无恶意模块，调试启动模式在无模块时进入 `debug_menu()`（`kernel_debug.c:932`），要求物理控制台交互；对无头远程场景主要构成启动流程干扰。

#### 最小复现假设

- 进程拥有正常 LeonOS ABI 访问能力即可（无需 `TASK_FLAG_SERVICE`、`TASK_FLAG_WINDOW_SERVER`，无需 `LEONOS_AUTH_ROLE_ADMIN`）。

#### 修复建议

- 在 `LEONOS_KERNEL_DEBUG_IOCTL_CONTROL` 分支前置 `require_kernel_debug_control()` 守卫，语义为：
  - `installer_mode` 内可放行；否则
  - 调用者必须是 `LEONOS_AUTH_ROLE_ADMIN` 或携带显式 `LEONOS_AUTHZ_KERNEL_DEBUG` 策略；或
  - 仅限受信任窗口服务器转发的、已完成桌面 UI 授权确认的请求。
- 对 `SET_ENABLED`、`ARM_NEXT_BOOT`、`CLEAR` 三个状态变更命令统一施加该守卫；`GET_STATE` 可保留为只读但仍建议限制为 admin/service。
- 回归测试：普通进程调用该 IOCTL 应返回 `-LEONOS_EPERM`，且 `/system/state/kerneldebug.enabled` 与 EFI 标记文件不应被创建/修改。

## 结构性建议（基于存活 8 项归纳）

| 维度 | 覆盖 | 建议 |
| --- | --- | --- |
| **统一授权守卫表** | F1 + F8 + 已修复的 FB/NET/DRIVER ioctl | 对所有"系统影响型" ioctl（电源、内核调试、display_request、appearance_request、网络配置、driver 控制、任务终止、NTP 同步）引入统一的 `require_*` 守卫表，由静态回归脚本确保每个 ioctl 常量在白名单内或被守卫调用。F1 与 F8 是当前最突出的两个裸调用分支。 |
| **存储层权限隔离** | F8 | `kernel_debug_control` 等内核内部函数直接调用 `storage_write_file`/`storage_mkdir`/`storage_write_boot_esp_file` 绕过 VFS。应将这些调用限制在已通过授权守卫的代码路径中，或为 `storage_*` API 增加可选的调用者身份参数以触发隐式权限检查。 |
| **协议长度安全基元** | F3 | 在 `userland/libc/src/libc.c` 和 `kernel/ntclks/net.c` 建立项目级安全算术包装；强制在 HTTP、TCP、DHCP、GUI 几何中使用差值型边界检查并对超长输入做 fail-closed。 |
| **状态绑定** | F4、F6、F7 | 网络状态机对每次"接受外部输入作为新状态"的动作，要求同时满足：(a) 身份绑定（服务器 IP/seq/查询 IP/MAC 一致性）；(b) 事务绑定（xid/等待中的查询/已请求地址）；(c) 协议正确性（接收窗口/RFC 兼容序号）。 |
| **明确不变量** | F2、F5 | 对"安全→不安全"方案/标志的退化建立项目级不变量：HTTPS 永不跟随至 HTTP；HTTPS-only Basic Auth 永不被明文请求加载。 |
| **回归门禁** | 全部 8 项 | 保持 `tools/test_security_regressions.py` 为源码只读检测，修复后以 `--strict` 纳入 CI；为 F8 新增 SEC-011 检测项（检查 `LEONOS_KERNEL_DEBUG_IOCTL_CONTROL` 分支是否包含 `authz_check` 或 `require_` 守卫）。 |
